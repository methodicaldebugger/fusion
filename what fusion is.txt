# Fusion Static Analyser

A small, dependency-free Rust crate scaffold for static analysis in Fusion.

## Layout

- `analyzer.rs` — runs registered analysis rules over a source file.
- `config.rs` — analyser configuration.
- `diagnostic.rs` — source locations and findings.
- `rule.rs` — common interface for analysis rules.
- `rules/` — individual rules.

The initial rules are deliberately conservative examples. They operate on a small
`SourceFile` abstraction rather than assuming Fusion's parser/AST API. Once Fusion's
AST is exposed as a library, rules can be upgraded to consume typed AST nodes and
symbol/type information.

## Use

```rust
use fusion_static_analyser::{Analyzer, SourceFile};

let analyzer = Analyzer::default();
let source = SourceFile::new("main.fus", "fn main() {\n    let unused = 1;\n}\n");
let diagnostics = analyzer.analyze(&source);

for diagnostic in diagnostics {
    println!("{diagnostic}");
}
```

the static analyser should identify opportunities and provide evidence, while a separate component decides whether to recommend a language transition and generates the message to the developer.

Example of the message Fusion could generate

Performance opportunity detected
Your image_processing() function accounts for 38% of the application's measured execution time and performs frequent memory allocations.
Suggested option: Consider implementing this module in Rust through Fusion's interoperability system.
Potential benefit: Lower allocation overhead and improved execution speed, subject to benchmarking.
Memory impact: May reduce temporary allocations, depending on the implementation.
Compatibility: Requires checking the module's data types and interoperability boundary.
Trade-off: Additional maintenance and cross-language integration complexity.
Recommendation only. Benchmarking and developer approval are required before migration.


The important part is that Fusion should not automatically assume another language will be faster. A language change can introduce FFI overhead, data conversion costs, memory ownership complications or additional maintenance. The analyser should distinguish between a potential performance gain and one demonstrated by benchmarks.

Where the five interoperability levels fit

I would make the Interoperability Advisor aware of Fusion's five levels, so it can recommend the least disruptive level that meets the requirement:
Low interoperability: Call an external component through a simple interface.
Higher interoperability: Share richer types, data and control flow.
Deep interoperability: Integrate more tightly with another language's runtime or memory model.

The exact descriptions should follow your planned five-level specification, but the general principle is to recommend only as much integration as necessary.


The analyser detects. The advisor evaluates. The recommendation generator explains. The developer decides. The orchestrator executes only after approval.

# Fusion interoperability model.

This crate defines the language/toolchain-neutral vocabulary for crossing the Fusion/foreign boundary. It deliberately contains no compiler process management. Foundry resolves *what* a project needs; 

the toolchain orchestrator decides *how/with which tools* to build it.

There are 5 layers of interoperability:
1. Native ABI: the foreign code is compiled into a static or shared library and linked into the Fusion binary. The foreign code is called directly from Fusion code, and vice versa, using the platform's native ABI.
2. Managed runtime: the foreign code is compiled into a library that is loaded into the Fusion process, and called via a managed runtime (e.g. JVM, CLR, etc.). The foreign code is called from Fusion code via the managed runtime's interop facilities, and vice versa.
3. Embedded runtime: the foreign code is compiled into a library that is loaded into the Fusion process, and called via an embedded runtime.
4. Process: the foreign code is compiled into a separate executable that is launched by the Fusion process. The foreign code is called from Fusion code via inter-process communication (IPC), and vice versa.
5. WebAssembly: the foreign code is compiled into a WebAssembly module that is loaded into the Fusion process, and called via the WebAssembly runtime.

Last but not least, what differentiates fusion and makes it a multi-billion dollar project:
Fusion architecture

1. Cloud toolchain provisioning
Automatically obtain the right compiler, SDK, linker, and plugin environment when needed. Developers shouldn't have to install every foreign toolchain on their machines.

2. Cargo-style package manager
Dependency resolution, lockfiles, workspaces, registries, version constraints, and a consistent package workflow.

3. Bazel-style build orchestration
Dependency graphs, incremental and parallel builds, remote caching, reproducibility, and the ability to coordinate components written in different languages.

4. Static analyser
Detect potential bugs, suspicious patterns, unnecessary complexity, and opportunities to use safer or more idiomatic code. An interoperability advisor could recommend existing libraries or foreign-language integrations, with the developer retaining control.

The architectural principle connecting these four components should be one project model. The package manager, build engine, analyser, and cloud workers should share dependency metadata, toolchain definitions, and configuration instead of maintaining separate systems.


Fusion programming language

1. Enums and exhaustive match
Model alternatives explicitly and make missing cases detectable at compile time.

2. Traits and generics
Enable reusable abstractions and compile-time polymorphism without relying on class inheritance.

3. Option and Result as foundational types
Represent absence and recoverable failure explicitly. Integrate them into the standard library and error-handling syntax rather than treating them as afterthoughts.

4. Indentation and braces
Support indentation-based blocks and brace-delimited blocks, with a clear, consistent parsing rule so developers can choose their preferred style.

5. Growable arrays as the primary collection
Keep the core collection model approachable. Hash maps and sets can still be available through the standard library when needed; they don't have to be separate built-in language constructs.

6. Traits for interoperability: a consistent way to describe capabilities, foreign-library wrappers, and generic APIs. The exact boundary between Fusion traits and foreign interfaces will need careful design.

7. Deterministic cleanup with defer: particularly important for a language with garbage collection. Memory reclamation and timely release of files, sockets, locks, and other resources are different problems.

Current status is getting Fusion bootstrap-ready.
Also making foundry.

Acording to claudeAI these things require our attention:

tuple types (tuple expressions exist, but Type has no tuple variant), Operator overloading and derives: no Add/Index/Deref traits, no #[derive], no attributes. Patterns: only wildcard, identifier, literal, and flat enum variant with bindings. Missing are nested patterns, guards (if), ranges, or-patterns (|), tuple and struct patterns, @ bindings, and ref patterns. Nested patterns, guards, and struct destructuring don’t exist yet.

Modules and packaging
import parses but is a no-op in the interpreter, resolver and checker, so there are effectively no modules, namespaces, use paths, re-exports or cross-file programs. pub/private exist but only on functions, structs and enums. There’s no equivalent of crates, Cargo, a registry, features, workspaces or build scripts.

Macros, tooling and ecosystem
Diagnostics have only six error kinds, which is a long way from rustc’s multi-span, suggestion-rich errors.

Bigger risks for your actual goal (C interop)
No FFI-capable types: you have num (i64) and float only. Real C APIs need fixed-width integers (int32, uint8, size_t), float32, byte buffers, opaque handles, struct layout, and callbacks. “No pointers” can stay true at the language level while the FFI layer has a restricted pointer-like type.
GC meets the ABI boundary: the native backend has no GC. The interpreter borrows the host’s Rc and clone semantics. Before Milestone 3 you need rules for passing GC memory to C (pinning versus copying), and defer must not depend on the GC, as you wrote.
Backend gaps: native code can’t yet do match, defer, for-each, break/continue, collections, or conversions. Self-hosting is blocked there first.


What we still need to implement:

tuple types, nested patterns, guards, ranges, or-patterns, and derives.

Diagnostics: rustc-quality errors with multiple spans and suggestions.

Real async fn/await exist, but functions run eagerly and return Task(value), so there’s no executor.

modules, because cross-file resolution, import paths, visibility and name collisions touch every stage and Foundry depends on them. Fixed-width integers also need casts and overflow rules in the checker, interpreter and backend.

Native runtime: this is the one to watch. Arrays, strings, closures and hash maps need a heap, so you need a runtime library and a GC strategy (tracing, reference counting, or arenas) before the backend can lower collections, defer and match. Self-hosting waits on this.

C interop: it needs more than types. You need foreign declarations, header-to-binding generation (parsing C headers is a project in itself), callbacks into a GC’d language, error mapping, and pinning rules.

Plugins can supply the language-specific mappings and policies for the first two items, but the core has to provide the substrate they sit on.

FFI types: if each plugin invented its own integer and buffer types, the checker couldn’t validate calls and plugins couldn’t share data. The core needs fixed-width ints, float32, bytes, an opaque Handle, struct layout control, and a callback type. Your self-hosting compiler also needs u8 and bytes for the lexer, so this isn’t only for interop.

GC and the boundary: defer can be the shared mechanism. Treat every foreign object as a resource with a deterministic close that defer runs, and keep GC finalizers as a safety net only. The policy then differs by layer:

Native ABI: copy by default, with explicit pinned buffers for zero-copy.
Managed runtime: handle tables, thread attach, and exception mapping.
Embedded runtime: bridge reference counts, plus the Python GIL.
Process: serialize everything, with no shared memory.
WebAssembly: copy through linear memory.

What you still need for 10+ languages
1. Count mechanisms, not languages. Most native languages reach you through the C ABI.
So a language plugin is mostly an adapter onto an existing layer, which is what makes 10+ realistic. Process and WebAssembly give the most breadth per unit of work.

2. A neutral interface description. Your interop model should define one language-neutral type system and signature schema. Each plugin then:
introspects its ecosystem (C headers, JVM class files, .NET metadata, Python stubs, rustdoc JSON, WIT);
generates Fusion binding files and glue code.

The schema needs ints, floats, strings (with encoding, since Java, C# and JS use UTF-16), bytes, lists, records, variants, resource handles, callbacks, and ownership annotations (borrowed, owned, out-param). The WebAssembly Component Model’s WIT and canonical ABI are the best reference, and Fusion’s Option, Result, structs and enums already map onto them.

3. A plugin SDK built like protoc plugins. Run plugins as separate executables that read a request and write generated files plus build steps. That makes them language-agnostic, versionable and sandboxable, which fits your point that build-running plugins are executable code. Ship a conformance test suite that every plugin must pass.

4. Cross-boundary rules the core must decide:
Errors: map exceptions, panics, errno and status codes into Result, and never unwind through an ABI.
Threads: decide how callbacks arriving on foreign threads enter the GC (safepoints), plus the GIL, JVM attach, and Go runtime init.
Diagnostics: error messages should name the foreign side.

5. Dynamic calls in the interpreter. Since you’re interpreter-first, layer 1 needs dlopen plus a libffi-style mechanism, or it only works in compiled builds. The process bridge has no such need, so it can prove a second strategy before the native backend is finished.

6. Foundry’s job: pinned, hash-verified toolchains per OS, hermetic builds, a lockfile of toolchains, and cross-compilation. On Windows, choose one ABI and linker story (MSVC-style versus MinGW) early, because mixing them breaks linking. Also budget for the binding generators: parsing C headers properly means using libclang, and every other language needs its own introspector.

Fusion needs a consistent way to describe its own types and foreign types.
Must have
- Primitive types: integers, floating-point numbers, booleans, characters, and strings.
- Fixed-width numeric types for ABI compatibility, such as i32, u64, and f64.
- Structs, enums, tuples, and arrays.
- Functions as values, including function pointers where appropriate.
- Generics and traits or equivalent abstraction mechanisms.
- Type inference with explicit annotations when necessary.
- A defined representation for nullable and optional values.
- A way to represent opaque foreign types.
- Compile-time type checking across module and plugin boundaries.
Fusion should also distinguish between a value's logical type and its physical representation.

Fusion needs an explicit policy for:
- Who owns a value.
- How long a value remains valid.
- Who releases resources.
- Whether a value can be borrowed temporarily.
- Whether a foreign object can outlive the call that created it.
- How callbacks and function pointers remain valid.
- What happens when an external runtime moves or collects an object.
- How resources are cleaned up after errors or cancellation.
My recommendation
Give Vanilla a safe default ownership model with explicit mechanisms for foreign boundaries.

A unified error model
Foreign functions can fail in many different ways:
- A Fusion function returns an error.
- A C function returns an error code.
- A C library sets a global error indicator.
- A Python call raises an exception.
- A Java method throws an exception.
- A subprocess exits unsuccessfully.
- A remote service times out.
- A WebAssembly module traps.
Vanilla needs a common way to represent and propagate failures without pretending they are all identical.

I recommend:
- Option<T> or an equivalent for values that may be absent.
- Result<T, E> or an equivalent for recoverable failures.
- Structured error values.
- A defined exception-boundary policy.
- Error conversion rules for foreign calls.
- Reliable cleanup when errors propagate.
- A way to preserve useful foreign error information.

A stable module and foreign-interface system
Fusion needs a standard way to describe what a module provides and what it depends on.

Fusion(vanilla/basic) should define:
- Module declarations and imports.
- Public and private visibility.
- Module identity.
- Symbol resolution.
- Dependency boundaries.
- Foreign function declarations.
- Foreign type declarations.
- Interface versioning.
- Name mangling and symbol naming rules.
- Linking and loading contracts.
- Rules for incompatible interfaces.


A plugin API with a stable contract
This is arguably the most strategically important component of Fusion.

The plugin system must be more than a collection of custom scripts. It needs a defined contract between Vanilla, Foundry, and ecosystem-specific tooling.

I would design the plugin API around six responsibilities.
Plugin responsibility                      What Vanilla or Foundry should provide
Ecosystem discovery                        Plugin identity, version, capabilities, and compatibility metadata
Compilation                                A standard way to request compilation and report diagnostics
Linking                                    A way to declare libraries, symbols, and linker requirements
Type integration                           A standard representation of foreign types and callable interfaces
Runtime integration                        A way to initialize, invoke, and clean up foreign runtime components
Build integration                          A way to declare dependencies, environment requirements, and build outputs


A standard runtime and capability model
Fusion needs to define which runtime services programs can rely on.

I would start with:
- Memory and resource-management interfaces.
- Task execution and synchronization.
- Process management.
- Basic file and environment access.
- Clocks and timers.
- Standard input and output.
- Dynamic library loading where supported.
- Diagnostics and runtime error reporting.
- A consistent initialization and shutdown lifecycle.


A programming language that crosses multiple ecosystems needs consistent debugging information.
Otherwise, errors become difficult to understand as soon as execution crosses a language boundary.

We should define a common diagnostic format that can represent:
- Source locations.
- Call stacks.
- Foreign function boundaries.
- Type errors.
- Build and link errors.
- Runtime failures.
- Task and cancellation errors.
- Foreign exceptions and error codes.
- Source mappings for generated code.

The developer should encounter consistent concepts and predictable behavior even when the implementation crosses language boundaries.
