# Fusion interoperability model.
This crate defines the language/toolchain-neutral vocabulary for crossing the Fusion/foreign boundary. It deliberately contains no compiler process management. Foundry resolves *what* a project needs. The toolchain orchestrator decides *how/with which tools* to build it.

There are 5 layers of interoperability:
1. Native ABI: the foreign code is compiled into a static or shared library and linked into the Fusion binary. Layer 1 has two forms: dynamic load for the interpreter and static link for AOT. The foreign code is called directly from Fusion code, and vice versa, using the platform's native ABI. Excellent interoperability. Very little overhead.
2. Managed runtime: means a GC’d VM such as the JVM or CLR, loaded in-process, with handle tables and thread attach. Is very powerful, but requires runtime integration.
3. Embedded runtime: means an interpreter such as CPython or Lua embedded in-process, with reference-count bridging and the GIL. It has more overhead, but is potentially extremely useful.
4. Process: the foreign code is compiled into a separate executable that is launched by the Fusion process. The foreign code is called from Fusion code via inter-process communication (IPC), and vice versa. The foreign library runs independently.
5. WebAssembly: the foreign code is compiled into a WebAssembly module that is loaded into the Fusion process, and called via the WebAssembly runtime. a very portable integration mechanism.

foundry.toml could eventually specify something conceptually like:

You may use libraries in other languages, not mentioned above, with a wrapper, binding, ABI boundary, generated bindings, RPC bridge, WebAssembly module, etc.

# Foundry - Fusion project/package/toolchain manager
The package manager for Fusion projects. It provides commands to create, build, run, and manage Fusion packages and their dependencies.
It is responsible managing dependency resolution, building Fusion programs, running and testing them, compatibility checks, publishing and more.
It resolves version, dependencies and compatibility issues for plugins. Bazel, in particular, already supports multi-language build orchestration, so Foundry should not rely on multi-language builds alone as its novelty. I should rely on Bazel(a multi-language build system) and Cargo(a package manager with dependencies and builds + reproducibility with cargo.lock) for guidance, knowledge and inspiration. Foundry: Supplies dependency resolution, build tooling, test execution, compatibility management and publishing.

I would divide Foundry into four responsibilities, each with a clearly defined boundary.
1. Package manager: Download and resolve dependencies. Manage package versions and a lockfile. Support local, Git, and registry dependencies.
Handle optional dependencies and features. Build and publish Fusion packages. Manage workspaces. This should be the foundation of Foundry, with predictable and reproducible dependency resolution.
2. Build requests: Foundry resolves what is needed (packages, plugins, toolchain versions, lockfile). Foundry should delegate compilation to the appropriate compiler instead of implementing the build logic of every language itself.
3. Plugin and toolchain manager: This is potentially the most distinctive part. Detect and provision compatible compilers, SDKs, and runtimes.
Install and update integration plugins. Check plugin and toolchain compatibility. Configure environment variables and compiler flags.
Generate or manage language bindings. Handle foreign-language integration strategies. For example, a C plugin could define how to compile C files, expose native libraries to Fusion, and link the resulting artifacts. Foundry could download or provision a C toolchain where licensing and platform constraints permit, rather than assuming the user has installed it.
4. Project workflow: This is the developer-facing experience. foundry new my_project, foundry add serde, foundry build, foundry run, foundry test, foundry doc, foundry publish.
Developers should not need to know which internal tool performs each operation. Foundry provides the unified interface while still allowing access to lower-level commands when needed. One important architectural decision is to separate packages, plugins, and toolchains. They are related, but they should not be the same thing.

Tuple types, basic patterns, and basic derives have their native-backend parity and generalization on the to-do list. module support is real, but it is not yet a fully unified module/type/package architecture. The native runtime is a major foundational gap. The archive has a beginning—particularly tracked allocations—not a finished memory-management system. C interop cannot safely expose arbitrary Fusion-managed values until we define their physical representation, lifetime, and ownership rules. concurrency primitives exist; real asynchronous execution does not. Phase 4 is a genuine new milestone. It also means we should not begin by adding a few FFI types to the parser. First we need a coherent ABI and build contract.

There is a surprisingly broad standard-library implementation in the interpreter. The documentation lists: - UTF-8 validation and encoding/decoding, string operations, and a regex engine - JSON and TOML parsing/serialization - SHA-256, HMAC, constant-time comparison, and secure random utilities - Time, date, timezone, and formatting functions - TCP networking, HTTP functionality, and optional TLS/HTTP/2 support - Filesystem and process operations - Channels, task spawning, work-stealing, structured scopes, and parallel operations - A test runner, benchmark support, and documentation generation. However, the documentation describes them as Rust interpreter implementations. We still need to check feature-by-feature which ones are available from compiled native Fusion programs, how robust the APIs are, and what portability guarantees they have. That distinction is particularly important for a general-purpose language: a library available only in the interpreter is not yet a complete cross-backend standard library.

A unified type system is essential. Fusion needs to distinguish a value's logical type from its physical representation. GC, defer, and foreign resources cannot be designed independently. The plugin system should be a first-class architecture, not a collection of scripts. Foundry already has a plugin descriptor model with plugin identity, version, capabilities, and requirements. That's a useful beginning. I particularly like the idea of using WIT and the WebAssembly Component Model as a reference for the neutral interface description. We should study its type and ownership concepts, but not assume Fusion must adopt the entire model. Fusion should have reliable text processing, file I/O, process execution, and a native runtime before we seriously pursue self-hosting.
